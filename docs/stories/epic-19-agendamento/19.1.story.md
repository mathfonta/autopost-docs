## Story
**As a** cliente que acabou de aprovar um post,
**I want** poder marcar esse post para ser publicado num horário futuro em vez de agora,
**so that** meu conteúdo saia no melhor horário mesmo que eu o tenha montado fora dele.

## Contexto / Motivação
Hoje o único caminho após `awaiting_approval` é `POST /content-requests/{id}/approve` (`app/api/content.py:420`), que seta `approved` e dispara `publish_post.delay()` imediatamente. Não existe estado de "agendado". Esta story cria a base de dados e a API de agendamento; a publicação automática no horário é a Story 19.2.

## Acceptance Criteria

1. **AC1 — Novo status:** O enum `ContentStatus` (`app/models/content_request.py:23`) ganha o valor `scheduled = "scheduled"`, posicionado conceitualmente entre `approved` e `publishing` no ciclo de vida.
2. **AC2 — Novo campo:** `ContentRequest` ganha `scheduled_for: Mapped[datetime | None]` **timezone-aware** (`DateTime(timezone=True)`), default `NULL`.
3. **AC3 — Migração:** Migração Alembic cria a coluna `scheduled_for` e adiciona o valor `scheduled` ao tipo enum, além do índice composto `(status, scheduled_for)` (necessário para o Beat da Story 19.2). Migração aplica e reverte sem erro.
4. **AC4 — Endpoint de agendar:** Novo `POST /content-requests/{id}/schedule` com body `{ "scheduled_for": "<ISO8601 com timezone>" }`. Só aceita posts em `awaiting_approval`. Seta `status=scheduled` + `scheduled_for` e **NÃO** chama `publish_post`. Retorna `{ id, status: "scheduled", scheduled_for }`.
5. **AC5 — Validações:** Rejeita (HTTP 422/400) `scheduled_for` no passado ou a mais de 30 dias no futuro. Rejeita (HTTP 409) se o status atual não for `awaiting_approval`. Rejeita (HTTP 403) se o post não pertence ao cliente autenticado (mesmo padrão do `/approve`).
6. **AC6 — Isolamento do caminho atual:** `POST /{id}/approve` permanece **byte-idêntico** — nenhuma mudança no fluxo "Publicar agora".
7. **AC7 — Testes:** Cobrem agendar com sucesso, `scheduled_for` no passado, > 30 dias, status errado, post de outro cliente, e a não-invocação de `publish_post` ao agendar.

## Dev Notes
- **Decisão de arquitetura (Aria):** endpoint **separado** `/schedule`, não parâmetro no `/approve` — zero risco de regressão no caminho crítico. Ver Architecture Review no `epic.md`.
- Espelhar a estrutura de `approve_content_request` (`app/api/content.py:420-455`) para auth/ownership/404, trocando o efeito final: em vez de `approved` + `publish_post.delay`, seta `scheduled` + `scheduled_for`.
- Schema Pydantic novo para o body (ex.: `ScheduleRequest { scheduled_for: datetime }`) em `app/schemas/content.py`.
- **@data-engineer:** a migração deve adicionar o valor ao enum Postgres (`ALTER TYPE ... ADD VALUE 'scheduled'` — atenção: não pode rodar dentro de transação em algumas versões; seguir o padrão das migrações de enum já existentes no projeto) e criar o índice `(status, scheduled_for)`.
- `scheduled_for` sempre timezone-aware; o Celery já opera em `America/Sao_Paulo` (`app/tasks/__init__.py`).
