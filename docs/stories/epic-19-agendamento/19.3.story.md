## Story
**As a** cliente prestes a agendar um post,
**I want** que o sistema me diga o melhor horário para publicar, com base em dados,
**so that** eu não precise adivinhar e meu post saia quando meu público está mais ativo.

## Contexto / Motivação
O agendamento (19.1/19.2) precisa de um horário sugerido para oferecer ao usuário. Esta story cria o endpoint que calcula esse horário a partir de dados reais, com degradação graciosa quando não há histórico suficiente.

## Acceptance Criteria

1. **AC1 — Endpoint:** `GET /insights/best-posting-time?format={content_type}` (autenticado) retorna `{ horario: "HH:MM", fonte, confianca }` onde `fonte ∈ {"historico", "exa", "fallback"}` e `confianca ∈ {"alta", "media", "baixa"}`.
2. **AC2 — Fonte histórico (prioridade 1):** Se o cliente tem **≥ 5 posts publicados** com métricas, agrega por hora-do-dia do `published_at` e escolhe a hora de melhor engajamento médio (likes + comments + reach). `fonte="historico"`.
3. **AC3 — Guarda de densidade:** Se a hora vencedora tiver < 2 posts, descartar o resultado de histórico e cair para a próxima fonte (evita "melhor horário" baseado em 1 post sorte).
4. **AC4 — Fonte Exa (prioridade 2):** Se não há histórico suficiente mas existe resultado da inteligência semanal do nicho (Exa, já rodando via `generate_weekly_intelligence`), usar o horário sugerido de lá. `fonte="exa"`.
5. **AC5 — Fallback (prioridade 3):** Sem histórico nem Exa → usar `copy_result.suggested_time` do próprio post (se disponível) ou `_DEFAULT_TIMES[segment]` (`app/agents/copywriter.py:31`). `fonte="fallback"`, `confianca="baixa"`.
6. **AC6 — Meta como fonte futura (NÃO nesta story):** A interface `{horario, fonte, confianca}` deve deixar espaço para uma futura `fonte="meta_audience"` como prioridade máxima, mas a v1 **NÃO** implementa Meta `audience_online` (bloqueado por App Review). Documentar o ponto de extensão.
7. **AC7 — Testes:** Cliente com ≥5 posts (histórico); cliente com 1 post na hora vencedora (guarda de densidade → cai pra fallback); cliente novo sem posts (fallback); formato do payload.

## Dev Notes
- **⚠️ Ancoragem de dados (CRÍTICO — decisão da Aria):** o "histórico próprio" vem de **`ContentRequest.publish_result`**, que contém `published_at` (setado em `app/tasks/pipeline.py:631`) e `metrics` (likes, comments, reach, impressions — coletados por `collect_metrics`). **NÃO** parsear os arquivos markdown do cérebro (`app/cerebro/writer.py`) — aqueles são contexto para LLM, não dados analíticos queryáveis.
- Query: `SELECT publish_result FROM content_requests WHERE client_id=? AND status='published'` → em Python, extrair `hour = published_at.astimezone(SP).hour` e somar engajamento de `metrics`, agrupar por hora.
- **Reuso (Aria):** o copywriter já produz `copy_result.suggested_time` por post e tem `_DEFAULT_TIMES` por segmento — usar como base do fallback, não recriar.
- `format` (content_type) pode refinar no futuro (Reels vs carrossel têm horários diferentes), mas v1 pode ignorar o filtro por formato se o volume de dados for baixo — documentar a decisão.
- Endpoint novo, provavelmente em `app/api/` (novo router `insights` ou dentro de `content.py`). Registrar no app.
