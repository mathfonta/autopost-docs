## Story
**As a** cliente prestes a agendar um post,
**I want** que o sistema me diga o melhor horário para publicar, com base em dados,
**so that** eu não precise adivinhar e meu post saia quando meu público está mais ativo.

## Contexto / Motivação
O agendamento (19.1/19.2) precisa de um horário sugerido para oferecer ao usuário. Esta story cria o endpoint que calcula esse horário a partir de dados reais, com degradação graciosa quando não há histórico suficiente.

## Acceptance Criteria

1. **AC1 — Endpoint:** `GET /insights/best-posting-time?format={content_type}` (autenticado) retorna `{ horario: "HH:MM", fonte, confianca }` onde `fonte ∈ {"historico", "exa", "fallback"}` e `confianca ∈ {"alta", "media", "baixa"}`.
2. **AC2 — Fonte histórico (prioridade 1):** Se o cliente tem **≥ 5 posts publicados** com métricas, agrega por hora-do-dia do `published_at` e escolhe a hora de melhor engajamento médio (likes + comments + reach). `fonte="historico"`.
3. **AC3 — Guarda de densidade:** Se a hora vencedora tiver < 2 posts, descartar o resultado de histórico e cair para a próxima fonte (evita "melhor horário" baseado em 1 post sorte).
4. **AC4 — Fonte Exa (prioridade 2):** Se não há histórico suficiente mas existe resultado da inteligência semanal do nicho (Exa, já rodando via `generate_weekly_intelligence`), usar o horário sugerido de lá. `fonte="exa"`.
5. **AC5 — Fallback (prioridade 3):** Sem histórico nem Exa → usar `copy_result.suggested_time` do próprio post (se disponível) ou `_DEFAULT_TIMES[segment]` (`app/agents/copywriter.py:31`). `fonte="fallback"`, `confianca="baixa"`.
6. **AC6 — Meta como fonte futura (NÃO nesta story):** A interface `{horario, fonte, confianca}` deve deixar espaço para uma futura `fonte="meta_audience"` como prioridade máxima, mas a v1 **NÃO** implementa Meta `audience_online` (bloqueado por App Review). Documentar o ponto de extensão.
7. **AC7 — Testes:** Cliente com ≥5 posts (histórico); cliente com 1 post na hora vencedora (guarda de densidade → cai pra fallback); cliente novo sem posts (fallback); formato do payload.

## Dev Notes
- **⚠️ Ancoragem de dados (CRÍTICO — decisão da Aria):** o "histórico próprio" vem de **`ContentRequest.publish_result`**, que contém `published_at` (setado em `app/tasks/pipeline.py:631`) e `metrics` (likes, comments, reach, impressions — coletados por `collect_metrics`). **NÃO** parsear os arquivos markdown do cérebro (`app/cerebro/writer.py`) — aqueles são contexto para LLM, não dados analíticos queryáveis.
- Query: `SELECT publish_result FROM content_requests WHERE client_id=? AND status='published'` → em Python, extrair `hour = published_at.astimezone(SP).hour` e somar engajamento de `metrics`, agrupar por hora.
- **Reuso (Aria):** o copywriter já produz `copy_result.suggested_time` por post e tem `_DEFAULT_TIMES` por segmento — usar como base do fallback, não recriar.
- `format` (content_type) pode refinar no futuro (Reels vs carrossel têm horários diferentes), mas v1 pode ignorar o filtro por formato se o volume de dados for baixo — documentar a decisão.
- Endpoint novo, provavelmente em `app/api/` (novo router `insights` ou dentro de `content.py`). Registrar no app.

### Completion Notes List

**Divergência de premissa descoberta antes de implementar (ver Change Log 1.2):** o AC4 assumia que a inteligência semanal do Exa (`generate_weekly_intelligence`, já rodando) produzia um "horário sugerido". Verificação do modelo `WeeklyContext` e da task mostrou que isso nunca existiu — só `summary` (tendências de mercado) e `hashtags`. Implementar o AC como estava escrito exigiria inventar um horário a partir de dados sem relação com engajamento. Levei a decisão ao usuário; ele optou por estender a captação real em vez de simplificar o escopo.

**O que foi implementado:**
- `app/models/weekly_context.py`: novo campo `suggested_time` (HH:MM).
- Migração `b2c3d4e5f6a7` (down_revision `a1b2c3d4e5f6`).
- `app/tasks/pipeline.py` (`generate_weekly_intelligence`): nova query Exa dedicada e evergreen (`days_back=365`, não é notícia da semana) — *"melhor horário para postar no Instagram construção civil Brasil"* — **mantida separada** das 3 queries de tendência de mercado, para não misturar sinal.
- `_extract_suggested_time(snippets)`: pede ao Gemini para extrair HH:MM **apenas** dos snippets da busca dedicada; se o Gemini não identificar um horário claro, retorna `None` — nunca "chuta" um valor. Testado com resposta válida, resposta "DESCONHECIDO", sem API key, sem snippets e com exceção do Gemini — todos os caminhos retornam `None` corretamente em vez de inventar.
- `GET /insights/best-posting-time` implementado em `app/api/insights.py` (reusa o router `/insights` já existente da Story 13.4, junto de `/weekly` e `/streak`), seguindo o padrão de cascata já usado em `/insights/strategy-recommendation` (Story 18.2).
- **AC2/AC3 (histórico + guarda de densidade):** agrega por hora (fuso `America/Sao_Paulo` via `zoneinfo`) a partir de `ContentRequest.publish_result` (`published_at` + `metrics`), exatamente como ancorado no Dev Notes. A guarda de densidade descarta o histórico **inteiro** (não busca uma segunda-melhor-hora) quando a hora vencedora tem menos de 2 posts — decisão confirmada durante os testes (um teste inicial meu presumiu o comportamento errado; corrigido para bater com o texto literal do AC3: "descartar o resultado de histórico e cair para a próxima fonte").
- **AC5 (fallback):** ajustado para usar só `_DEFAULT_TIMES[segment]` — o `copy_result.suggested_time` "do próprio post" não se aplica a este endpoint genérico (sem contexto de post específico); fica reusado do lado do frontend na Story 19.4, como já estava no Dev Notes original.
- **Achado extra:** o endpoint irmão `/insights/weekly` usa `getattr(current_client, "business_segment", None)` — esse atributo **não existe** no modelo `Client` (só `brand_profile` como JSONB), então sempre cai no fallback `"geral"`. Bug pré-existente da Story 13.4, fora do escopo desta story — **não copiei esse padrão**; o endpoint novo lê `client.brand_profile.get("segment")` corretamente (mesmo padrão já usado em `list_themes`).
- **AC6:** `fonte` é uma string simples (`"historico" | "exa" | "fallback"`), documentado no docstring do endpoint como ponto de extensão para `"meta_audience"` quando o App Review aprovar — não implementado, conforme escopo.

### Reconhecimento

A decisão do @dev de **parar em vez de inventar** quando descobriu que o AC4 tinha premissa falsa (Exa não produzia horário) é exatamente o comportamento certo diante da regra de não-invenção deste projeto. ### 🔴 Bug encontrado (achado de QA, não do @dev)

**BUG-001** — `app/api/insights.py:184-191` compara `client.brand_profile.get("segment")` (texto livre do onboarding, sem normalização garantida) com `WeeklyContext.segment` (hardcoded `"Construção civil"`, capital C, em `app/tasks/pipeline.py`) via `==` exato. Como o restante do código usa segmento em minúsculo (`_DEFAULT_TIMES`, `scout.py`), a comparação provavelmente **nunca bate** para clientes reais — a fonte Exa (AC4) fica inacessível na prática, mesmo com o dado real disponível, e o sistema cai silenciosamente no fallback estático. A cascata de 3 fontes documentada no AC1 funciona como 2 na prática.

**Isso não é um bug do @dev nesta implementação isoladamente** — é uma incompatibilidade entre um dado pré-existente (`WeeklyContext.segment` hardcoded há tempos) e um dado novo (`brand_profile.segment`, usado pela primeira vez neste endpoint). Mas como está no caminho crítico do AC4 desta story, entra no gate dela.
