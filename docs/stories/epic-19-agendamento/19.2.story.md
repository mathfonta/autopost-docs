## Story
**As a** cliente que agendou um post,
**I want** que ele seja publicado automaticamente no horário marcado, e poder cancelar ou reagendar antes disso,
**so that** eu não precise estar presente no horário e ainda tenha controle sobre a fila.

## Contexto / Motivação
A Story 19.1 cria o estado `scheduled` + `scheduled_for`. Esta story adiciona o executor que efetivamente publica no horário, reusando a task `publish_post` existente (`app/tasks/pipeline.py:517`), e os endpoints para o usuário gerenciar o agendamento.

## Acceptance Criteria

1. **AC1 — Beat a cada minuto:** Nova task Celery `publish_scheduled_posts` registrada no `beat_schedule` (`app/tasks/__init__.py`) com `crontab(minute="*")`.
2. **AC2 — Claim atômico (idempotência):** A cada tick, o executor reivindica as linhas devidas com um único UPDATE atômico:
   ```sql
   UPDATE content_requests SET status='publishing'
   WHERE status='scheduled' AND scheduled_for <= now() RETURNING id;
   ```
   Para cada `id` retornado → `publish_post.delay(id)`. **Dois ticks concorrentes nunca publicam o mesmo post duas vezes** (só um pega a linha no `RETURNING`).
3. **AC3 — Fuso correto:** `scheduled_for <= now()` compara corretamente no fuso `America/Sao_Paulo` (Celery já configurado). Um post agendado para 19h de Brasília dispara às 19h de Brasília, não em UTC.
4. **AC4 — Endpoint cancelar:** `POST /content-requests/{id}/schedule/cancel` (ou `DELETE`) devolve o post de `scheduled` para `awaiting_approval` e zera `scheduled_for`. Só funciona em posts `scheduled`.
5. **AC5 — Endpoint reagendar:** `PATCH /content-requests/{id}/schedule` com novo `scheduled_for` atualiza a data mantendo `status=scheduled`. Reusa as validações de futuro/≤30d da Story 19.1.
6. **AC6 — Ownership/status:** Cancelar e reagendar respeitam ownership (403) e só operam em `scheduled` (409 caso contrário).
7. **AC7 — Testes:** Cobrem: publicação disparada quando `scheduled_for` já passou; NÃO disparada quando ainda é futuro; idempotência (simular dois claims — só um publica); cancelar volta para `awaiting_approval`; reagendar atualiza a data; publicação real reusa `publish_post` (mockado).

## Dev Notes
- **Decisão de arquitetura (Aria):** o Beat NÃO faz select-depois-update; faz o UPDATE...RETURNING que já reivindica. Ver Architecture Review no `epic.md`.
- **Reuso:** `publish_post` (`app/tasks/pipeline.py:517`) já seta `publishing` e já tem guarda `if status==published: return` — reusar sem alteração. O `publishing` setado pelo claim atômico é redundante e inofensivo.
- O UPDATE atômico deve usar a sessão async do projeto (`_run_sync` + SQLAlchemy) seguindo o padrão das outras tasks Celery em `pipeline.py`. Pode-se usar `update(...).where(...).returning(ContentRequest.id)`.
- Registrar a task ao lado de `weekly-content-intelligence` e `supabase-keepalive` no `beat_schedule` (`app/tasks/__init__.py:21`).
- Índice `(status, scheduled_for)` criado na Story 19.1 garante que o Beat de 1 min não faça full scan.
- **Semântica de cancelar (decisão travada):** volta para `awaiting_approval` — NÃO vira `rejected`. O conteúdo já aprovado é preservado; o usuário pode publicar agora, reagendar ou rejeitar explicitamente depois.

- `publish_scheduled_posts` (Celery task, `app/tasks/pipeline.py`) implementa o claim atômico exatamente como resolvido no Architecture Review: um único `UPDATE content_requests SET status='publishing' WHERE status='scheduled' AND scheduled_for<=now() RETURNING id`, e dispara `publish_post.delay(id)` para cada linha retornada. Nenhuma alteração em `publish_post`.
- Registrada em `beat_schedule` (`app/tasks/__init__.py`) como `publish-scheduled-posts`, `crontab(minute="*")`.
- Endpoints `POST /{id}/schedule/cancel` e `PATCH /{id}/schedule` adicionados em `app/api/content.py`, logo após o endpoint de agendar da Story 19.1. Extraí a validação de janela temporal (futuro, ≤30 dias) para uma função compartilhada `_validate_scheduled_for` — usada tanto por `/schedule` quanto por `PATCH /schedule` (reagendar), evitando duplicação.
- Cancelar segue a semântica travada no epic: `scheduled → awaiting_approval` (não `rejected`) e zera `scheduled_for`.
- **Sobre testar idempotência sem Postgres real:** a garantia de atomicidade do `UPDATE...RETURNING` é uma propriedade do motor de banco (row-level locking do Postgres), não algo que dá para provar com mock. O que os testes cobrem é o comportamento observável: quando o claim não reivindica nenhuma linha (simulando que outro tick já pegou tudo), `publish_post.delay` não é chamado de novo — e a query em si foi inspecionada (`test_publish_scheduled_posts_query_filters_status_and_time`) para confirmar que filtra por `status='scheduled' AND scheduled_for<=now()` e usa UPDATE...RETURNING. A prova definitiva de não-duplicação em concorrência real só vem de teste de integração contra Postgres — fora do escopo de testes unitários mockados.
